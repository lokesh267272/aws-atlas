# Module 3: S3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Module 3 to AWS Atlas: six visual-first S3 lessons following Mealhop's files, each visual preceded by a short, easy explanation, each lesson with a challenge.

**Architecture:** Same shape as Module 2. Each lesson keeps its rules in a pure-TypeScript model (`*Model.ts`) tested with Vitest, including a test that its "Show me" solution passes. React visuals sit on top. Shared pieces come first: an `Explain` block with Module 3 text limits, the story and storage-class data (one source of numbers for lessons 3, 5 and 6), shared glossary terms, and the "Your file store so far" diagram. Lessons 1–5 are then built in parallel; lesson 6 reuses their models.

**Tech Stack:** Vite 8, React 19, TypeScript 7, Tailwind v4, `motion`, `@react-three/fiber` + `drei` (lesson 1 only), Vitest 5.

**Spec:** `docs/superpowers/specs/2026-11-09-module-3-s3-design.md`. Read it first; this plan argues from it. Module 2's code (`src/modules/ec2/**`) is the pattern to copy.

## Global Constraints

- **Lesson layout:** intro (one `Prose` block, 1–2 sentences, ≤ 40 words) → for each teaching visual (1 or 2): `<Explain>` then its `Bench` → the challenge (inside the last visual's `Bench` or its own `Bench`) → `<FileStoreDiagram step={n} />`.
- **Explanation:** 2–4 sentences, ≤ 70 words, always visible, **at most 2 per lesson**, never on a challenge-only `Bench` or the diagram. Each lesson has at least one everyday comparison in an explanation.
- **"Try it" line:** `Bench intro`, 1 sentence, ≤ 22 words. Challenge feedback: 1 sentence. "In real AWS": at most 1 per lesson, 1–2 sentences.
- No `Takeaways`, no `Checkpoint`, no "Check yourself". The Task 1 checker enforces the numbers above.
- Every AWS term in copy is wrapped in `<Term>`. Never redefine a key that exists in `src/course/glossary.ts`, `src/modules/foundations/**/terms.ts` or `src/modules/ec2/**/terms.ts` (e.g. `s3`, `bucket`, `object`, `object-key`, `encryption`, `identity-based-policy`, `resource-based-policy`, `explicit-deny`, `iam-role`, `instance-profile`, `ebs`, `ebs-volume`, `availability-zone`, `vpc`). Terms needed by more than one lesson live in `src/modules/s3/terms.ts` (Task 2). A lesson adds only keys no other lesson needs; if it needs a shared one that's missing, it reports it instead of adding it.
- No glossary `<Term>` inside a `<label>` (the Module 2 test pattern enforces this).
- 3D only in lesson 1, visual B, via `Scene3D`. Controls sit outside the canvas, `Bench tone="screen"`, drei `<Html>` labels use a fixed `portal`.
- Motion only on learner action; under `prefers-reduced-motion`, jump to the end state.
- Colour carries meaning only: Region teal dashed, AZ blue dashed, VPC purple, S3 = the `storage` category colour. No new palettes, no ALL-CAPS eyebrows, no "→" on buttons, no decorative gradients.
- Phone width: 16px gutter, no horizontal scroll. Every challenge is solvable with the keyboard only; every drag has a click or select alternative.
- Prices come only from `src/modules/s3/storageClasses.ts` and are labelled with a short "Example prices" tag.
- Local resources only. `npm test`, `npm run typecheck` and `npm run build` pass.
- Don't modify `src/modules/foundations/**` or `src/modules/ec2/**`. Shared-file edits are only the ones named in Tasks 1–3.
- Work on branch `module-3-s3` (already created, spec committed). **Never push.** Pushing to `main` redeploys the public site.

## Review Focus

1. **Odd bucket names** (empty, spaces, capitals, `_`, a trailing `-`, `..`, `192.168.1.1`, 64 characters, pasted with spaces around it): the learner gets a clear one-line reason and nothing crashes. Tested in Task 4 (`bucketNameProblems`).
2. **No WebGL or a 3D crash in lesson 1:** the lesson still teaches through the 2D fallback, and the challenge doesn't depend on the 3D at all. Tested in Task 4 (SSR render has the goal and its button; `Scene3DView webgl={false}` renders the fallback).
3. **Out-of-order clicks:** run the intern's script twice, restore before anything was deleted, move the clock backwards, Reset mid-run. Models stay valid. Tested in Tasks 5, 7 and 8 (idempotence and no-op cases).
4. **Numbers that disagree between lessons** (a class costs one thing in lesson 3 and another in lesson 6). Tested in Task 9: the final model's first-month storage cost for a placement equals lesson 3's `runMonth` for the same placement.
5. **Changing the setup after solving:** the challenge shows Module 2's "stale" line instead of a stale success. Checked by hand in Task 11; each lesson passes `stale` to `Challenge` the way `src/modules/ec2/lessons/*` do.

## Lessons (Tasks 4–8 run in parallel; Task 9 after them)

**How to run Tasks 4–8 (from Module 2):**
- One builder per lesson, each in its own git worktree off `module-3-s3` after Task 3, branch `s3-<id>`.
- Junction `node_modules` into each worktree: `cmd /c mklink /J node_modules "<repo>\node_modules"`.

- Merge each lesson branch into `module-3-s3` after its review passes.
