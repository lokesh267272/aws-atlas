# Module 2: EC2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Module 2 to AWS Atlas: six short, visual-first EC2 lessons about a food delivery app. Each lesson has a challenge, one-line captions and no paragraphs.

**Architecture:** Each lesson keeps its rules in a small pure-TypeScript model file (`*Model.ts`), unit-tested with Vitest, including a test that its "Show me" solution passes its challenge. React visuals sit on top of the models. Three shared pieces are built first: a `Challenge` panel, a `Scene3D` frame, and a "Your setup so far" diagram. Then each lesson is built in its own folder. A text-budget test renders every lesson to HTML and fails if paragraphs creep back.

**Tech Stack:** Vite 8, React 19, TypeScript 7, Tailwind v4, `motion`, `@react-three/fiber` + `drei`, and Vitest 5 (new dev dependency, supports Vite 8).

**Spec:** `docs/superpowers/specs/2026-10-22-module-2-ec2-design.md`. Read it first. This plan argues from it.

## Global Constraints

- Text: one caption sentence per visual, "at most about 20 words", in `Bench intro`. Enforced as ≤ 22 words and 1 sentence.
- Lesson intro: one sentence in a single `Prose` block. No other `Prose`, no `Takeaways`, no `Checkpoint`.
- At most one `Callout kind="real-aws"` per lesson, one sentence.
- Every AWS term in copy is wrapped in `<Term>`. Before adding a term, search `src/course/glossary.ts` and every `src/modules/foundations/lessons/*/terms.ts` for an existing key (e.g. `ec2`, `instance`, `security-group`, `instance-profile` already exist) and reuse it. Never redefine a key; the Task 4 test enforces this.
- 3D only in lessons 1 and 6, via `Scene3D`. All controls sit outside the canvas. Use the dark `Bench tone="screen"`.
- Motion only on learner action. Respect `prefers-reduced-motion` (jump to the end state).
- Colour carries meaning only: Region teal dashed, AZ blue dashed, VPC purple, service colours from `src/course/categories.ts`. No new palettes, no ALL-CAPS eyebrows, no "→" on buttons, no decorative gradients.
- Phone width: 16px gutter, no horizontal scroll. Every challenge must be solvable with the keyboard only. Any drag needs a click alternative.
- Prices are example prices with realistic ratios, labelled with a short "Example prices" tag. Stated discount facts (e.g. Spot "up to 90% off") must match AWS docs.
- Local resources only (no CDNs). `npm run typecheck`, `npm run build` and `npm test` must pass.
- Don't modify Module 1 (`src/modules/foundations/**`). The only shared-file edits allowed are the ones named in this plan's tasks.
- Work on branch `module-2-ec2`. Never push. Pushing redeploys the public site.

## Review Focus

1. **No WebGL or a 3D crash** (lessons 1 and 6): the lesson still teaches, and its challenge can still be solved through the 2D fallback. Tested in Tasks 3, 5 and 10 (SSR render contains the goal and its controls; `Scene3DView` with `webgl={false}` renders the fallback).
2. **Clicking mid-animation or out of order** (Launch twice, Stop while pending, Reset during a run): the state must stay valid. Tested through the `transition()` invalid-action cases in Tasks 5 and 7, and the `simulateDay` determinism test in Task 10.
3. **"Show me" must actually solve.** Each model exports its `solution` and a test asserts it passes. Tasks 5 to 10.
4. **Copy that claims something AWS doesn't do**, e.g. "AWS won't launch without a key pair". It is checked in the Task 11 fact audit. The launch model treats "No key pair" as a valid choice (tested in Task 5).
5. **Phone width and keyboard-only play.** Checked by hand in Task 12. No automated test, because the project has no DOM test environment.

### Task 7: Lesson 3 `storage` — Disks that remember

**Files:** `src/modules/ec2/lessons/storage/`: `storageModel.ts`, `storageModel.test.ts`, `DiskLab.tsx`, `SnapshotChallenge.tsx`, `Lesson.tsx`, `terms.ts`

**Interfaces:**
- `type Disk = 'ebs-root' | 'ebs-extra' | 'instance-store'`
- `type DiskAction = 'reboot' | 'stop' | 'start' | 'terminate' | 'host-failure'`
- `survives(disk: Disk, action: DiskAction): boolean`
- `type ServerState = 'running' | 'stopped' | 'terminated'`
- `transition(s: ServerState, a: DiskAction): ServerState`. Invalid actions return `s`.
- Scenario:
  - `SCENARIO`: ordered events `'maintenance-stop' | 'replace-server' | 'shop-closes' | 'volume-failure'`, with orders arriving between events.
  - `runScenario(choice: { ordersOn: Disk; snapshotAfter: ScenarioEvent | null }): { ordersLost: number; lostAt: ScenarioEvent | null }`
  - `solution`

  **Plan's call:** the spec's "trouble in its AZ" event becomes a **volume failure** (rare but real). An AZ outage makes a volume unreachable rather than destroyed, and lesson 6 owns AZ outages. Snapshot honesty: orders after the last snapshot are lost if the volume is lost. The volume failure happens after `shop-closes`, so a snapshot taken at closing time loses nothing.

- [ ] **Step 1: Model tests:**

```ts

  ['ebs-extra', 'stop', true], ['ebs-extra', 'terminate', true], ['ebs-extra', 'host-failure', true],

it('cannot start a terminated server or stop a stopped one', () => {

it('extra volume without snapshot loses orders at volume failure', () => { expect(runScenario({ ordersOn: 'ebs-extra', snapshotAfter: null }).lostAt).toBe('volume-failure') })
```

### Task 10: Lesson 6 `scale` — Survive and scale (3D) + final challenge

Runs after Tasks 5–9. It may import those models (e.g. `inboundAllowed`, `CATALOG`, `PRICE_PER_SERVER_HOUR`) instead of redefining them.

**Files:** `src/modules/ec2/lessons/scale/`: `scaleModel.ts`, `scaleModel.test.ts`, `RegionScene.tsx` (r3f), `RegionFallback.tsx` (SVG), `FleetControls.tsx`, `BuildItAll.tsx`, `Lesson.tsx`, `terms.ts`

**Interfaces:**
- `interface FleetConfig { ami: string | null; instanceType: string; webOpen: boolean; azCount: 1 | 2 | 3; min: number; max: number; targetCpu: number; ordersOn: 'server-disk' | 'database'; burst: 'on-demand' | 'spot' }`
- `type FleetEvent = { at: number; kind: 'rush' | 'instance-crash' | 'az-down' | 'spot-interruption' }`
- `DAY_EVENTS: FleetEvent[]`: a lunch rush and an AZ outage overlapping its tail. The outage hits the AZ holding the database primary, so failover is exercised.
- `interface Tick { t: number; demand: number; perAz: number[]; served: number; turnedAway: number; lostOnServers: number; dbFailingOver: boolean; cost: number }`
- `simulateDay(cfg: FleetConfig, events?: FleetEvent[]): { ticks: Tick[]; lostOrders: number; cost: number; solved: boolean }`. It is pure and deterministic.
  - Target tracking sets desired capacity, clamped to [min, max]. New instances take a fixed number of ticks to boot.
  - The ASG spreads instances across `azCount` AZs. The ALB routes only to healthy instances.
  - `az-down` kills that AZ's instances, and replacements launch in the remaining AZs.
  - Database failover pauses orders for 1–2 ticks. They queue and are **not lost**.
  - `ordersOn: 'server-disk'` loses the orders stored on any instance that disappears.
  - `lostOrders = turnedAway + lostOnServers`.
  - `solved = lostOrders === 0 && cost ≤ DAY_BUDGET`.
- `DAY_BUDGET`, `solution: FleetConfig`

- [ ] **Step 1: Model tests:**

```ts

it('is deterministic', () => { expect(simulateDay(solution, DAY_EVENTS)).toEqual(simulateDay(solution, DAY_EVENTS)) })
it('one AZ means the outage turns customers away', () => { expect(simulateDay({ ...solution, azCount: 1 }, DAY_EVENTS).lostOrders).toBeGreaterThan(0) })
it('orders on server disks are lost when servers disappear', () => { expect(simulateDay({ ...solution, ordersOn: 'server-disk' }, DAY_EVENTS).lostOrders).toBeGreaterThan(0) })
it('database failover pauses but loses nothing', () => { const r = simulateDay(solution, DAY_EVENTS); expect(r.ticks.some(t => t.dbFailingOver)).toBe(true); expect(r.lostOrders).toBe(0) })
it('closed web port turns everyone away', () => { expect(simulateDay({ ...solution, webOpen: false }, DAY_EVENTS).lostOrders).toBeGreaterThan(0) })
it('max too low cannot absorb the rush', () => { expect(simulateDay({ ...solution, max: solution.min }, DAY_EVENTS).lostOrders).toBeGreaterThan(0) })
it('Spot burst behind the ALB loses capacity, not orders', () => {
  const r = simulateDay({ ...solution, burst: 'spot' }, [...DAY_EVENTS, { at: 5, kind: 'spot-interruption' }]); expect(r.ticks.some(t => t.lostOnServers > 0)).toBe(false)
})
```
